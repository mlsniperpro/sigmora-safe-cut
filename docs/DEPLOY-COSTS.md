# Deploy: scale to zero, EgoBlur on a GPU, and what it costs

The service on Modal (`deploy/modal_app.py`) sleeps when no one uses it, and its audit runs Meta's EgoBlur Gen 2 on a
GPU. This page is the reasoning and the arithmetic; the code's own comments say the same thing where it applies.

## What runs where

| Piece | Container | When it runs |
|---|---|---|
| `SafeCutApi` (FastAPI, the pipeline's worker threads, YuNet fallback) | 1 core, 2 GiB; `min_containers=0`, `max_containers=1`, `scaledown_window=300` | From the first request after a quiet spell until 300 s after the last input |
| `SafeCutApi.hold` | the same container (an input of it) | While a job is mid-action: Modal never scales down a container with an input in flight |
| `egoblur_detect` (EgoBlur Gen 2, torch) | L4 (T4 when no L4 is free), 2 cores, 6 GiB; `scaledown_window=30` | One call per audit scan, reading the render from the handoff Volume `safecut-audit` |
| `cleanup` (24 h deletion, wakes stranded jobs) | 0.125 core, 128 MiB (Modal's default request, the smallest), `scaledown_window=2` | Every 15 minutes |

## Cost

Estimates from `modal billing rates` (<https://modal.com/pricing>, read 2026-10-31: CPU $0.0473 per core-hour,
memory $0.008 per GiB-hour, L4 $0.80 and T4 $0.59 per hour) and the sizes above. The run times are assumptions
until a deployed run's receipts and Modal's usage page replace them. Generated by `python -m deploy.costs`
(`tests/test_deploy.py` keeps this table, the one in `docs/SUBMISSION.md` and the code in step):

```text
Modal cost (estimate)        What runs                                                 USD  per
Idle, before (always on)     API, 2 cores + 4 GiB, all day                          3.0384  day
Idle, now (scaled to zero)   cleanup cron only, 96 runs of ~14 s                    0.0026  day
A visit's quiet tail         API stays up 300 s after the last request              0.0053  visit
One 60 s clip, API           ~300 s of the API container                            0.0053  clip
One 60 s clip, GPU audit     ~210 s on an L4, plus its 30 s tail                    0.0628  clip
One clip, GPU worst case     what the estimate reserves: 930 s                      0.2454  clip
```

Modal bills a container's CPU and memory at whichever is higher, its request or its use, so the request is what an
idle container costs and a busy one may burst past it (a render uses about 2 cores for seconds). Meta's own spend
per clip is separate and unchanged (`docs/API-NOTES.md` §9.2). Every GPU call's estimate goes into the job's
`cost.jsonl` (`provider: "modal"`, `estimated: true`), the spend ledger (the job cap and the caller's caps)
and the receipt (`cost_usd_gpu`); the up-front check on `POST /start` adds the GPU's worst case
(`safecut/api/access.py`).

## Decisions

- **Keeping a started job alive: an input of the same container (`hold`), not a worker thread.** Modal scales a
  container down once no input has been in flight for `scaledown_window` (<https://modal.com/docs/guide/cold-start>);
  a thread isn't an input. Every queued action spawns `SafeCutApi().hold(job_id)`, which with
  `max_containers=1` can only land on the container running the job, and returns when the job stops. Rejected: a
  separate job function on the Volume (two containers writing the SQLite ledger and `state.json` on one Volume,
  which Modal Volumes don't make safe), and the cron alone (a job would stall up to 15 minutes at a time). The cron
  stays as the backstop: it spawns `hold` for any job still mid-action, which wakes a container whose start
  re-queues it (`Service.recover`), resuming at the first stage whose output isn't fresh, so a finished stage is
  never paid for twice. A job found mid-action by a restart after 45 minutes, or on its fourth restart, fails as `internal` instead of waking a container again and again (a job still running in a live container is left to finish).
  Proven by `tests/test_scale_to_zero.py`: a local API is killed with SIGKILL mid-analysis and mid-audit; a fresh
  process finishes the job, its receipt verifies, and every stage logs exactly one `done`.
- **Deploys stop the old container right after publishing (`modal deploy --strategy recreate`).** Modal's default, `rolling`, lets old
  containers drain while new ones start (modal 1.6.2 `app.py`, `deploy`); a running job's `hold` input would keep the
  old one draining while the new one's start resumed the same job, two writers on one Volume, paid twice. With
  `recreate` Modal publishes the new version and then stops the old containers, waiting up to 40 s for them (modal
  1.6.2 `runner.py`; a stop that takes longer only warns). The old API container goes at once (its service stops
  without waiting for running jobs, from the ASGI lifespan, which Modal ends first, and from `@modal.exit`, and its
  job threads are daemons the interpreter doesn't wait for), so the overlap is the few seconds between the publish
  and that exit: a deploy is in effect one restart, and the job resumes once, from its last finished stage. Pushes
  during judging are barred anyway (BLOCKED.md).
- **The demo is rebuilt beside the one being served.** A new deploy's code, or a demo YuNet had to audit (retried at
  most every 6 hours), is built in a scratch folder and swapped in only when done; a failed build leaves the old demo
  up. The build has a ledger of its own (the owner's spend, under the job cap), so the service's ledger keeps one
  writer.
- **`scaledown_window=300`.** Longer than the per-minute rate window (a sleep can't reset a window that's still
  open) and long enough that a judge reading a result between clicks finds the API awake; each sleep costs at most
  the quiet tail in the table.
- **Rate limits across a sleep.** The per-minute limit stays in memory (see above); the per-hour paid-action limit
  moved to SQLite on the jobs Volume beside the spend ledger (`StoredRateLimiter`), so a wake never hands a
  client a fresh hour. The daily USD cap was already in the ledger on the Volume. Both are tested across a restart.
- **Cold start.** The API's import path went from ~1.06 s to ~0.74 s by importing scipy only where the binding
  stages need it (measured in this sandbox, three runs each, with `python -c "import time; t = time.perf_counter();
  import safecut.api.app; print(time.perf_counter() - t)"`). The web app waits up to 60 s for its first request, retries
  only idempotent calls, and says "Waking Safe Cut up" after 4 s (`web/src/lib/wake.ts`).
- **GPU: L4 first, T4 as the fallback.** EgoBlur Gen 2 is two detector passes per frame; the L4 has several times
  the T4's FP32 throughput (30.3 vs 8.1 TFLOPS: [L4](https://www.nvidia.com/en-us/data-center/l4/),
  [T4](https://www.nvidia.com/en-us/data-center/tesla-t4/)) for 1.36× the price, so it should cost less per clip as well as finish sooner. Modal's GPU
  list (`gpu=["L4", "T4"]`) takes a T4 when no L4 is free; the price setting assumes the dearer L4.
- **The render reaches the GPU through a handoff Volume.** The API copies the render to `safecut-audit` (under one
  lock), commits that Volume, and the GPU function reloads it and reads `redacted.mp4` itself; only frame numbers go
  out and boxes come back, and the answer carries the render's SHA-256, so a stale Volume view is caught and
  retried. Not the jobs Volume: in modal 1.6.2 `Volume.commit()` reloads the Volume afterwards, and a reload fails
  while files are open on it, which the API always has (the ledger's and the limiter's SQLite files). The cron
  removes any handoff an audit left behind. The weights' SHA-256 is checked before use.
- **The audit always runs.** A timeout, an error (retried once), missing or altered weights, no GPU, or a cap that
  can't cover the call: YuNet runs instead, and `audit.json` (`egoblur.model`, `egoblur.device`), the
  receipt (`auditor`, `auditor_device`) and `raw/audit/gpu.json` say which ran and why. A GPU that drops out
  after pass 1 makes the audit run again, whole, on YuNet, so no audit mixes detectors.

## What a crash or a fallback costs, honestly

- A finished stage is never run again after a restart, so its Meta calls are never repaid. The stage a kill
  interrupted does run again from its inputs, and its calls are paid again; the job cap bounds that, and a SIGKILL's
  open ledger reservation keeps counting as spent (failing closed: `LocalLedger` counts every reservation not
  released). After three restarts the job fails.
- A GPU that answers pass 1 and then fails a re-check makes the audit run again, whole, on YuNet, on the patched
  render: the red team is asked again about frames whose pixels changed, and those calls are paid. Rare, and bounded
  by the job and daily caps.
- The up-front estimate counts one GPU scan per audit pass at its timeout; a transient failure's one retry is
  reserved call by call, so the ledger's caps still hold it. The GPU function has no Modal-level retries, so every
  attempt Modal bills is one the API reserved and priced.
- GPU dollars count against the same job, daily, code and pilot caps as Meta's (conservative: a cap protects the
  owner's total spend), and are shown apart on the receipt (`cost_usd_gpu`).

## Where it would break first

- The handoff Volume holds a copy of the redacted render (never the upload) while its audit runs; the audit removes
  it and commits the removal when it ends, and the 15-minute cron removes any copy older than 35 minutes that a
  dead container left, so a copy is gone within the hour (ten minutes to spare for the cron's own latency). The privacy page says so.
- A GPU answer over 2 MiB comes back through Modal's blob storage, a host replay's network guard doesn't let
  through: a replayed (demo-mode) audit of a very crowded clip falls back to YuNet, named as such. Live jobs aren't
  under the guard.

- The spend ledger is SQLite on the jobs Volume. If a torn snapshot ever leaves it unreadable, the API refuses to
  start (it fails closed: no spend without a ledger). The fix is the owner's: `modal volume get safecut-jobs
  jobs/ledger.sqlite` to keep a copy, then `modal volume rm safecut-jobs jobs/ledger.sqlite` (the day's caps then
  start from zero, so lower `SAFECUT_DAILY_USD_CAP` for that day).

- One API container serves everyone: past `SAFECUT_MAX_ACTIVE_JOBS` (8) concurrent jobs, start and render answer
  429. That is the design (one ledger writer), not an accident.
- A cold start adds time to the first request after a quiet spell (an estimate of 10 to 40 s until a deploy
  measures it: the deploy check prints the first request's wait); the web app says so.
- A burst of audits queues on the GPU function; each scan waits at most `SAFECUT_AUDIT_GPU_TIMEOUT_S` (300 s)
  before the audit falls back to YuNet.
